IntentOS framework guide

Build by intent.
Learn the whole system.

This guide takes you from an empty directory to a tested, deployable server-rendered application. It is the canonical reference for the current IntentOS runtime.

01 / Beginner

Quick start

IntentOS is a Node.js runtime for server-rendered applications. Create an application, start the development server, then edit application-owned files.

npx intent-os create my-store
cd my-store
npx intent-os generate schema
npx intent-os dev

Open http://localhost:3000. The root page is the framework landing page, /docs is the developer portal, and the generated application pages are served by the same runtime.

Verify before changing code

npx intent-os test
npx intent-os generate schema --check

02 / Concepts

The mental model

You describe the application surface and domain model. The runtime supplies routing, rendering, validation, sessions, CSRF, database access, transactions, and HTML fragment enhancement.

Intentpages · schema · config
→
Runtimeroute · compile · validate
→
SystemHTML · SQLite · state

IntentOS is intentionally constrained. It is strongest for server-rendered, form-heavy, data-backed sites and ecommerce workflows. It is not a replacement for React, a general visual builder, or a universal backend for arbitrary workloads.

03 / Application

Project structure

my-store/
├─ pages/                 # routes and declarative HTML
├─ src/data/              # application-owned seed/catalog data
├─ public/                # application browser assets
├─ schema.js              # source-of-truth data model
├─ schema.sql             # generated schema artifact
├─ migrations/            # additive database changes
├─ app.config.js          # runtime configuration
├─ theme.css              # application styling
└─ package.json           # application scripts

The framework owns the runtime under framework/. Do not edit generated schema.sql by hand; edit schema.js and regenerate it.

04 / Reference

Pages, routes, and syntax

Every HTML file under pages/ is a route. index.html represents the directory route. Square brackets create dynamic parameters.

pages/index.html           → /
pages/products/index.html → /products
pages/products/[slug].html → /products/:slug
pages/docs/guide.html      → /docs/guide

Resource lists

<x-list of="Product" as="product" page="24">
  <article>
    <a href="/products/{{product.slug}}">
      <h2>{{product.name}}</h2>
      <x-money value="{{product.price}}" currency="EUR" />
    </a>
  </article>
</x-list>

Records and control flow

<x-record of="Product" by="slug" as="product">
  <h1>{{product.name}}</h1>
  <x-if test="product.active">Available</x-if>
  <x-each in="product.tags" as="tag">{{tag}}</x-each>
</x-record>

Interpolation is HTML-escaped by default. The compiler does not evaluate arbitrary JavaScript expressions.

05 / Data

Schema and data

schema.js defines tables, columns, constraints, foreign keys, and the schema version. The ecommerce starter includes products, categories, carts, orders, payments, webhook events, customers, and sessions.

export default {
  version: 1,
  tables: {
    notes: { columns: {
      id: { type: 'TEXT', primaryKey: true },
      body: { type: 'TEXT', notNull: true },
    } },
  },
};

Runtime resources expose intent-level operations such as Product.list(), while SQL stays inside the framework adapter. Values are parameterized; application pages do not write SQL.

06 / Interaction

Actions and forms

Actions name framework-owned domain operations. The same form works with JavaScript disabled and can be enhanced into an HTML fragment request.

<form method="post" action="/_app/action/cart.add" data-action="cart.add">
  <input type="hidden" name="productId" value="{{product.id}}">
  <input type="number" name="quantity" value="1" min="1" max="99">
  <button type="submit">Add to cart</button>
</form>

Built-in actions include auth.login, auth.logout, cart.add, cart.update, cart.remove, order.create, order.cancel, and checkout.create.

Use data-fragment="cart-summary" and data-fragment-target="cart-summary" for replaceable HTML regions.

07 / Runtime

State and navigation

Persistent business state belongs on the server. The browser runtime manages only enhancement state such as pending controls, navigation, focusable fragments, and status messages.

  • GET requests render complete HTML documents.
  • Enhanced requests can replace targeted fragments.
  • POST actions validate CSRF and input before mutation.
  • Successful ordinary forms redirect; enhanced forms receive HTML fragments.
  • Prices, inventory, payment state, and ownership are never trusted from the browser.

08 / Production

Security model

  • All mutations require a session-bound CSRF token.
  • Inputs reject unknown fields and validate domain constraints.
  • Cart prices are read from database truth.
  • Orders are checked against session or customer ownership.
  • Sessions rotate on login and logout.
  • HTML interpolation is escaped.
  • Stripe webhooks require raw-body signature verification.
  • Production requires INTENT_OS_SESSION_SECRET.

Local email login is an identity scaffold, not proof of email ownership. Add a verified passwordless or OAuth provider before accepting real accounts.

09 / Operations

Schema changes

# edit schema.js
npx intent-os generate schema
npx intent-os generate migration add-customer-phone
npx intent-os test
npx intent-os generate schema --check

Migrations are applied transactionally and recorded in _intent_os_migrations. The generator rejects removed tables, removed columns, changed existing columns, and unsafe non-null additions.

10 / Integration

Payments

IntentOS uses Stripe-hosted Checkout. The server creates a Checkout Session from the authoritative order total. The browser never receives the Stripe secret. Payment completion is driven by:

POST /_app/webhooks/stripe

Configure STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, public HTTPS, and a persistent database before live payments.

11 / Quality

Testing

npm test
npx intent-os test
npm run check

Test malformed input, missing products, duplicate operations, ownership violations, transaction rollback, webhook replay, and no-JavaScript form fallback. Browser acceptance should cover keyboard navigation, mobile layouts, back/forward navigation, and failed requests.

12 / Launch

Deployment checklist

  1. Use Node.js 22.5 or newer.
  2. Set NODE_ENV=production.
  3. Set a stable high-entropy INTENT_OS_SESSION_SECRET.
  4. Mount SQLite on a persistent single-host volume.
  5. Run schema checks and migrations before traffic.
  6. Configure Stripe secrets and webhook HTTPS.
  7. Add an identity provider for verified accounts.
  8. Configure backups, logs, monitoring, alerting, and restore drills.
  9. Do not run multiple writers against the same SQLite file.

13 / Advanced

Boundaries and extension

IntentOS is currently an opinionated server-rendered ecommerce runtime. It supports custom pages, styles, catalog data, additive schema changes, and framework-owned actions. It does not currently provide a general component compiler, arbitrary client expressions, a visual layout generator, distributed caching, a PostgreSQL adapter, or a production identity provider.

When a requirement falls outside the supported model, extend the framework deliberately: add a resource/action contract, tests at the server boundary, documentation, and an explicit escape hatch. Do not silently place business authority in browser JavaScript.
